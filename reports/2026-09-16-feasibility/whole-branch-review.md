## 优点

- SDK 保持框架无关，Demo 与 Vanilla 都消费公开接口；没有引入 Detection runtime 或自动多人逻辑。固定 256×192 FP32、COCO 17 点、原图坐标、原始响应分数和 DARK 路径，与设计及双语文档一致。
- 主线程与 Worker 共用数学和执行实现，显式后端没有静默回退；单在途约束、调用者像素副本、会话/tensor/Worker 释放和缓存摘要验证分工清晰。既有官方数学夹具，也有独立的真实模型及公开 SDK 验收。
- 模型 ZIP、源码、ONNX 和测试输入身份有记录；张量探针、完整 SDK 图片路径、Demo 与发布范围明确分开。当前没有伪称 npm/Hub/正式 Demo 已发布、全量 AP 已重测、手机或 NPU 已兼容。
- SDK 构建复制同版本 ORT 与模块 Worker，npm 文件范围不包含 ONNX；React 为开发依赖。Demo 使用相对资产路径，生产构建与 Vanilla 路径一致。390px 最终截图无按钮重叠，结果与图片同屏，次要信息折叠展示。
- CI 文件使用只读默认权限；草稿发布工作流按作业限定写权限，当前 alpha 被发布检查拒绝。公开分发与远程治理留在独立里程碑，符合本轮范围。

### Important

1. **[P2] 图片解码期间允许对旧图运行，导致旧关键点显示在新图上**

   文件：`demo/src/App.tsx:212`、`:223`、`:225`、`:248`。

   `pick()` 在开始时更新 generation 并清除结果，但等待 `img.decode()` 时保留旧 `blob/source`，也没有输入加载状态阻止 `run()`。此时发起的 run 捕获的是新 generation 和旧 blob，因而结果可以正常通过 generation 检查。新图随后完成解码时只替换图片，没有清除这个期间生成的旧图结果。

   最小定向复现已在现有生产 preview、Chromium `153.0.8010.12` 完成：先加载并识别 `person.jpg`；让下一张真实 40×60 PNG 的 `HTMLImageElement.decode()` 完成通知等待一个可控 Promise；上传后运行按钮仍为 enabled；运行旧图成功后释放解码 Promise。最终文件名为 `new-image.png`、画布为 `[40,60]`，关键点计数仍为旧图的 `17 / 17`，状态为“图片已就绪”。这会使结果与用户看到的输入不一致。

   建议：将图片获取/解码纳入明确的在途输入状态，解码前使旧输入不可运行；原子提交图片身份与结果失效，并让 run 结果严格绑定已提交的图片版本。添加上述交错行为断言，不能仅等待“图片已就绪”后再运行。

2. **[P2] 示例请求没有绑定请求发起时的 generation，旧请求可以覆盖重置或后选图片**

   文件：`demo/src/App.tsx:236`、`:238`、`:242`，关联重置 `:417`。

   `example()` 在 fetch 完成后才调用 `pick()` 分配新的 generation，示例请求本身不参与取消或过期检查。因此用户在请求未完成时执行的重置或上传会被旧请求当成更新输入覆盖；重置增加 generation 无法使这个请求失效。

   最小定向复现已完成：已有 `person.jpg` 时，再点击示例并暂缓该次图片请求；点击重置后确认 `canvasCount=0` 且状态为“选择一张单人图片开始”；继续该请求后自动变为 `canvasCount=1`、文件名 `person.jpg`、状态“图片已就绪”。该行为不需要运行模型。

   建议：在示例点击时取得输入操作 token，并在 fetch、blob、decode 的成功和失败边界检查该 token；重置、另一次选择和卸载均取消或使其过期。旧请求的 catch 也不得覆盖最新状态。补充延迟示例请求后重置/重新上传的验收断言。
